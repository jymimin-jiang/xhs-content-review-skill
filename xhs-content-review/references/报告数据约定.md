# HTML报告数据约定

生成UTF-8 JSON。示例见 `../examples/review.json`，所有示例为虚构，不复制到真实报告。脚本只渲染既有判断，不进行OCR或合规检测。

根字段：`title`、`report_id`、`date`、`scenario`、`materials`、`issues`、`pending`。广告引用还需`ad_scope`：confirmed（明确适用）/ conditional（待确认）。conditional不能仅凭广告规则作必须禁用，pending须说明广告场景待确认。

可选`demo`（真实报告false）、`excluded`、`advice`。

materials数组每项：
- `id`：唯一英文字母/数字/下划线/连字符ID。
- `type`：text / image_ocr / image_visual。
- `label`：标题、正文第2段，或图片01（封面）等。
- `location`：文件名及区域，未知封面不猜。
- `text`：忠实原文/OCR；视觉材料写客观画面描述并注明非OCR。
- `status`：read / partial / unread。不确定的小字不得填成确定文字。
- `image_path`：可选，用户已提交图片的本地路径；相对路径按JSON文件目录解析。仅PNG/JPEG/WebP，最大20MB；否则提示未嵌入。不要通过猜测路径搜集无关文件。

issues数组每项：
- `id`、`title`、`level`（必须禁用/高危）、`action`（建议删除/建议改写）。
- `reason`：完整上下文判断、适用行业及条件，说明不确定性和反证。
- `evidence`：数组，每项`material_id`、`quote`（原文精确片段）、`location`。同一句多处相同出现时全部标红；不同语境需拆分材料为段落/区域以避免多标。image_visual不填quote，用location定位。
- `sources`：数组，每项`kind`（platform/user）、`id`、`title`、`location`、`excerpt`、`status`。platform ID必须在source-index.json；user ID必须以XHS-USER-开头且提供`rule_text`，仅填用户实际启用的规则。
- `suggestion`：删除范围或具体建议改写，不虚构事实。
- `conditions`：使用前提/未确认项；无额外条件时明确说明，不留空。

pending：字符串数组，识别不清/缺资料等，不作风险等级。没有risk时issues填空数组。不能给每个未知事项硬加一个高危问题。

渲染器会校验来源ID和原文精确匹配，但不能验证来源适用性、摘录是否忠实或AI判断正确；生成前必须与参考原文核对。所有字段作为纯文本转义，不传入HTML。输出不覆盖已有文件，复查生成新版本。

## 报告展示规范（2026-10-29更新）

`content_title`填写笔记标题或用户确认的简短主题，不写“本地测试”等测试标识。页面标题自动拼接date的YYYYMMDD格式＋content_title＋“敏感词审查报告”；没有content_title时兼容使用title。date使用实际报告日期的YYYY-MM-DD。

HTML来源仅展示来源名称及相关原文，不展示规则ID、条款编号、采集方式和快照版本。ID、位置、status仍完整保留在JSON中用于审核与追溯，不能因页面简化就省略数据。不要在sources.title或excerpt内重复塞入编号或采集状态；原文中真实出现的数字保留。免责声明采用12px。
